# Orchestrator-Worker Pattern

The orchestrator-worker pattern is an architecture in which a central coordinator plans work, delegates specialized tasks to workers, monitors execution, and combines outputs into a final result. In LLM-based systems, the orchestrator is often a top-level agent and the workers are sub-agents, tools, or runtime-specific executors.

This concept is a core organizing idea in [[summaries/agentic-workflows]] and closely relates to [[concepts/multi-agent-orchestration]] and [[concepts/subagent-architecture]].

## Core Structure

The pattern separates responsibilities into two roles:

- **Orchestrator**: receives the high-level goal, decomposes it into subtasks, routes each task, tracks progress, handles retries, and assembles the final output
- **Workers**: perform narrower, specialized tasks such as data loading, cleaning, redaction, code execution, retrieval, analysis, or report drafting

This separation helps complex workflows remain modular, observable, and easier to extend.

## Role in Agentic Workflows

In [[summaries/agentic-workflows]], the motivating use case is an end-to-end data science and clinical reporting pipeline. A top-level agent may receive a goal such as producing a neuropsychological or clinical report, then delegate stages like:

- data ingestion
- data processing
- PII or PHI redaction
- table creation
- figure generation
- narrative report generation

This makes the pattern especially relevant to [[concepts/neuropsychological-assessment-pipeline]], [[concepts/neuropsychological-reporting]], [[concepts/clinical-narrative-generation]], and [[concepts/pii-redaction-pipelines]].

## Why Use This Pattern

The orchestrator-worker pattern is useful when a task:

- spans multiple stages with different tools or skills
- requires coordination across files, services, or runtimes
- benefits from specialized components rather than one general agent doing everything
- needs explicit control over execution order, retries, and output assembly

In practice, this supports cleaner decomposition than a single monolithic agent. It also fits systems where some steps are deterministic and others are generative.

## Cross-Language Execution

A key detail from [[summaries/agentic-workflows]] is that workers may operate in different language environments. In the `luria` / `cingulate` example, a Python-based orchestrator coordinates logic implemented partly in R. That means the orchestrator must manage:

- invocation of R code from Python
- data exchange between runtimes
- error handling across language boundaries
- consistent tracking of intermediate state

This makes the pattern relevant to [[concepts/r-python-integration]], [[concepts/cingulate-engine]], and [[concepts/luria-neuropsych-pipeline]].

## Relationship to State and Memory

Because orchestrated tasks often unfold over many steps, the pattern depends on explicit state handling. The orchestrator may need to track:

- which subtasks are pending, running, or complete
- outputs generated by each worker
- retry history and failure reasons
- shared context needed by downstream steps

Related ideas include [[concepts/agent-pipeline-state-management]], [[concepts/agent-memory]], and [[concepts/persistent-memory]].

## Interaction with Retrieval and Tool Use

Workers do not have to be full agents. They may instead be tools or specialized execution units. Common worker capabilities include:

- retrieval from a knowledge source using [[concepts/retrieval-augmented-generation]]
- role-specific routing via [[concepts/role-based-llm-routing]]
- report parsing and extraction in [[concepts/report-ingestion-pipeline]]
- deidentification through [[concepts/phi-deidentification-pipeline]]

This makes the pattern compatible with both tool-based and agent-based systems.

## Autonomy and Review Boundaries

The pattern also supports selective autonomy. The orchestrator can let workers execute low-risk steps automatically while requiring human review for sensitive outputs. In clinical workflows, that often means routine transformations can run silently, while high-stakes decisions such as redaction review or final report sign-off should be escalated.

This links the pattern to [[concepts/silent-operation]], [[concepts/clinical-data-privacy]], [[concepts/phi-data-handling]], and [[concepts/privacy-first-software]].

## Strengths

- modular decomposition of complex tasks
- easier specialization of worker roles
- better observability and error isolation
- support for multi-stage and long-running workflows
- compatibility with mixed deterministic and generative components
- flexibility across different runtimes and tools

## Risks and Failure Modes

- poor task decomposition can create fragile pipelines
- orchestration overhead may add latency and complexity
- worker outputs may be inconsistent without strong interfaces
- hidden state can make failures difficult to debug
- cross-language boundaries can complicate retries and serialization

These risks make disciplined architecture and logging important, connecting to [[concepts/decision-logging]] and [[concepts/python-logging]].

## In Clinical and Research Pipelines

The pattern is especially valuable in domains where many structured steps lead to a final narrative output. In neuropsychological and clinical workflows, it can coordinate extraction, interpretation, redaction, retrieval, synthesis, and rendering while preserving oversight boundaries.

Relevant related concepts include [[concepts/clinical-ai-copilot]], [[concepts/neuropsychological-assessment-automation]], [[concepts/narrative-report-generation]], and [[concepts/modular-report-architecture]].
