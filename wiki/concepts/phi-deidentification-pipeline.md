# PHI De-identification Pipeline

PHI (Protected Health Information) de-identification is the process of automatically detecting and redacting personally identifiable clinical data from documents before they are stored, indexed, or used in downstream processing. In systems that handle sensitive medical records, de-identification is a mandatory step to comply with privacy regulations (such as HIPAA) and to enable safe use of clinical data for research or machine learning purposes.

## Role in Clinical Neuropsychological Report Pipelines

In both the [[summaries/AUTISM_RAG_SYSTEM_DOCUMENTATION]] and the neuropsychological report RAG pipeline described in [[summaries/NEUROPSYCHOLOGICAL_REPORT_RAG_CODEMAP]] and [[summaries/NEUROPSYCHOLOGICAL_REPORT_RAG_PIPELINE]], PHI de-identification is embedded directly into the **clinical report ingestion pipeline**. It is not a separate post-processing step but an integral stage that runs before any data is written to the vector store.

### Location in the Pipeline

```
process_single_report()
├── parse_pdf()                      — extract raw text (PyMuPDF / fitz.open)
├── parse_report()                   — extract structure and diagnoses
└── deidentify_recommendations()     — redact PHI
    ├── strip_page_artifacts()       — remove headers, footers, name lines
    ├── _infer_patient_name_from_text()     — fallback name detection
    ├── _infer_patient_name_from_source_file()
    ├── build_report_replacements()  — build patient-specific patterns
    ├── apply patient-specific replacements (name hash placeholders)
    └── apply GENERAL_PHI_PATTERNS   — SSN, phone, email, MRN safety nets
```

The function `deidentify_recommendations()` is called in `src/ingest_recommendations.py:47` (implemented in `src/report_deidentify.py`) and operates on structured text extracted from neuropsychological reports before chunks are generated and embedded. After de-identification, the pipeline proceeds through embedding generation and population of a FAISS vector index — see [[concepts/faiss-vector-index]].

## Multi-Stage De-identification Process

The pipeline runs through five distinct stages:

### Stage 1: Strip Page Artifacts
Before any PHI-specific redaction, `strip_page_artifacts()` (`report_deidentify.py:237`) removes structural document noise:
- CONFIDENTIAL headers
- Page numbers
- Standalone name lines that appear as running headers or footers

### Stage 2: Patient Name Inference (Fallback Chain)
The pipeline infers patient identity through a prioritized fallback chain when metadata extraction may have missed it:
1. Search for `"Name: First Last"` pattern in text (`report_deidentify.py:101`)
2. Search CONFIDENTIAL footer lines (`report_deidentify.py:112`)
3. Search standalone name lines (`report_deidentify.py:123`)
4. Fall back to inferring from the source filename via `_infer_patient_name_from_source_file()` (`report_deidentify.py:244`)

This fallback chain ensures robust detection even when report formatting is inconsistent across clinicians or institutions. It is a concrete example of the [[concepts/fallback-strategy]] pattern applied to clinical NLP.

### Stage 3: Build Patient-Specific Replacement Patterns
`build_report_replacements()` (`report_deidentify.py:246`) constructs an ordered list of regex patterns targeting:
- **Name variants** — generated by `_name_forms()`, which produces multiple surface forms of the patient name (full, first-only, last-only, initials, etc.). Patterns are ordered longest-first to prevent partial-match errors.
- **Dates** — evaluation dates, dates of birth, and other temporal identifiers (`report_deidentify.py:211`)
- **Case numbers** — clinical record numbers and other unique identifiers (`report_deidentify.py:219`)

### Stage 4: Apply Patient-Specific Replacements
All patient-specific patterns are applied via `pattern.sub()` (`report_deidentify.py:254`), replacing matched PHI with **deterministic hash-based placeholders** generated by `_short_hash()` (`deidentify.py:82`). This produces a consistent 6-character hash for the same patient across multiple reports, enabling:
- Consistent anonymization within a patient's record set
- Auditability — the same patient always receives the same token
- Safe downstream use without re-identifying individuals

This is directly related to [[concepts/redaction-tokens]], which covers token-level patterns used in redaction workflows more broadly.

### Stage 5: Apply General PHI Safety Nets
Two layers of general-purpose patterns (`report_deidentify.py:257–259`) sweep up any PHI not caught by patient-specific rules:
- `GENERAL_PHI_PATTERNS` — Social Security Numbers, phone numbers, email addresses
- `REPORT_GENERAL_PHI_PATTERNS` — residual dates, medical record numbers (MRNs)

## What Gets Redacted

The pipeline targets the following categories of PHI:

| Category | Examples |
|---|---|
| **Names** | Patient, guardian, clinician names in all surface forms |
| **Dates** | Dates of birth, evaluation dates, appointment dates |
| **IDs** | Case numbers, MRNs, Social Security Numbers |
| **Contact info** | Phone numbers, email addresses |

After redaction, the de-identified text is chunked and embedded, meaning the [[concepts/faiss-vector-index]] never contains raw PHI.

## Design Rationale

Embedding de-identification within ingestion rather than applying it at query time or post-storage provides several advantages:

1. **Defense in depth** — PHI never enters the vector store, eliminating the risk of leakage through retrieval.
2. **Auditability** — every stored chunk is guaranteed to be de-identified at rest.
3. **Downstream safety** — LLM prompts constructed from retrieved chunks are also PHI-free, preventing accidental exposure through API calls to external providers such as Anthropic or OpenAI.
4. **Consistency** — deterministic hashing ensures the same patient always maps to the same anonymized token, supporting longitudinal use without re-identification.

This approach aligns with [[concepts/privacy-first-software]] principles and is particularly important when using cloud-based LLM providers that may log or retain prompt content. The [[summaries/NEUROPSYCHOLOGICAL_REPORT_RAG_PIPELINE]] document confirms this design: de-identification occurs at `ingest_recommendations.py:47`, well before embeddings are generated at `ingest_recommendations.py:186` or written to disk.

## Relationship to Diagnosis Parsing and Metadata

De-identification applies to the **free-text content** of report chunks, but structured metadata (diagnoses, age groups) is retained in a standardized, non-identifying form. Diagnosis codes are normalized using DSM-5 mappings (see [[concepts/dsm5-diagnosis-normalization]]) and stored alongside embeddings to support filtered retrieval without re-exposing PHI. This separation means clinically useful signal is preserved for semantic search while patient identity is protected.

Specifically, the diagnosis extraction pipeline (via `extract_diagnoses()` in `report_parser.py`) runs in parallel with de-identification and produces structured metadata — ICD-10 codes, DSM-5 categories, canonical names — that is stored non-identifying alongside embeddings. See [[concepts/icd10-diagnosis-extraction]] for details on that process.

## Integration with the Recommendation RAG Pipeline

The de-identification pipeline feeds directly into the [[concepts/recommendation-rag-pipeline]]:

```
PDF ingestion (PyMuPDF)
  → PHI de-identification          (report_deidentify.py)
  → recommendation chunking        (report_parser.py)
  → embedding generation           (embeddings.py / SentenceTransformer)
  → FAISS vector store             (retrieval.py)
  → filtered semantic search       (retrieval.py — k×3 over-fetch + metadata filter)
  → LLM recommendation generation  (llm.py — Anthropic/OpenAI/Ollama via LangChain)
```

Because de-identification occurs before chunking, every `RecommendationChunk` stored in the vector index is guaranteed PHI-free, regardless of how it is later retrieved or formatted into LLM prompts. The over-fetch strategy (retrieving k×3 candidates before metadata filtering) in [[concepts/faiss-vector-index]] search ensures recall is maintained without compromising privacy by filtering post-retrieval rather than pre-redaction.

## Summary

PHI de-identification in clinical neuropsychological report pipelines is a multi-stage pre-storage process that strips page artifacts, infers patient identity through a fallback chain, builds patient-specific regex replacement patterns, applies deterministic hash-based substitutions, and sweeps with general PHI safety nets. Implemented in `src/report_deidentify.py` and orchestrated from `src/ingest_recommendations.py`, the five-stage process ensures that no protected health information enters the vector store or is exposed to external LLM APIs. Deterministic 6-character hashing enables consistent anonymization across multiple reports for the same patient. Structured metadata such as diagnosis codes and age groups is preserved in non-identifying form alongside embeddings, maintaining clinical utility while protecting patient identity. This is a foundational requirement for any clinical AI system handling real patient data.
